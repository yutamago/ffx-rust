# Draw-diff gate captures (M4 item 3, docs/drawdiff.md "Scene gates"):
# a hash-mode capture of three frames of the Thunder Plains travel agency
# (kami0100, save ffx_005, indoor), at ctrl work 0's count 101 (as
# event-agency-1, menu-grid). A battle started from here (`battle 33 0 3`)
# was tried and dropped: its load took 127 or 128 frames in original runs,
# and the later frame gave 31 more draws (draw-gate-deck.txt has the battle).
# Needs the graphics layer (FFX_GFX=1); not part of run-all.sh. Run it
# through tools/scene-gate-capture.sh, or
#   FFX_GFX=1 target/release/examples/replay tools/replays/draw-gate-kami.txt \
#     '<windows folder>\draw.trace' [original]
# Captures land beside the trace ($OUT\kami0100):
# keep them in ~/ffx-work/m4/captures, never in git. Compare two runs with
# tools/scene-gate.sh kami0100 <run A> <run B>.
#
# `pin` (docs/harness.md, "Pinned state") right after `lockstep on`, as
# field-walk and draw-field do. Until 2026-10-27 the load ran free and the
# pin waited for the map's event (count 64); since then the load runs in
# lockstep (`load direct ... lockstep`) and sound keeps the update count
# (docs/harness.md, "Sound in lockstep"), so the pin falls on the same
# update of the load in every run. Pinned at count 64, five original
# kami0100 runs still differed in `scene.GlobalTime`, the cloth ring and
# the eye-blink texture: the 64 updates before it ran on the time the free
# boot left (those captures: dg-<replay>-pin64-q*). References dg-<replay>-q1/q2. Each
# capture is `gfxcapture ... now async` at a boundary the script reached
# in lockstep: it holds the next three updates exactly (the harness checks
# the updates the frames show and fails the reply otherwise).
load direct 5 kami0100 lockstep
lockstep on
pin
waitfor 0x01325d94:4 40000000 c0ffffff 1500
wait 37
read 0x01325d94 4
readp 0x00ccb9d8 0xfaf4 4
gfxcapture $OUT\kami0100 hash frames 3 now async
wait 3
gfxcapture result
