# M6: ports (survey, 2026-11-15)

Linux and the Steam Deck first, then macOS (`docs/rewrite-plan.md`,
"M6: ports"). This is the survey that opens M6: what ties `ffx-rust` to
Windows, the graphics back end to choose, and a proof of concept. The
full plan with the work packages and gates is kept outside the repo
(`~/ffx-work/m6/m6-plan.md`). The user decided (2026-11-15): Proton now, the platform seam, and native platforms later through a Godot frontend; no wgpu back end for now (`docs/rewrite-plan.md`, "M6: ports"). The graphics comparison below stays as the record of the options.

**2026-11-27 (user):** native platforms after all: playable `ffx-rust`
on Windows x64, macOS ARM64, Linux x64 and Linux ARM64, no Godot
frontend for now. The wgpu back end below (the recommendation) is back
on, with a native platform for Linux and macOS (`docs/rewrite-plan.md`,
"M6: ports"); it is in `ffx-host` since 2026-11-28 ("The wgpu back
end", below). The release `ffx-rust` already compiles for all four
targets (checked 2026-11-27, `--no-default-features --features swf`).

## Where it stands

- The release `ffx-rust` (`--no-default-features --features swf`)
  already compiles for x86_64 Linux, and the Linux check boots it on the
  null device. Game logic is platform-free: the x87 and C runtime maths
  are software models, Vorbis uses the `libm` crate, the mixer plain f32.
- Windows-only at run time: the window and its messages (33 imports),
  the host's DirectInput, XInput and raw input, WASAPI output, the D3D11
  back end, `steam_api64.dll`, the arena's write watch,
  `TerminateProcess` and `ffx-launch`. Since the platform seam
  (2026-11-15, `docs/host.md`, "The platform seam") all of these but the
  arena and `ffx-launch` sit behind one trait, `ffx_host::platform::Platform`,
  with the Windows code as `WindowsPlatform` and the Linux check's
  stand-ins as `HeadlessPlatform`.
- Small portability items besides: `cpuid` must answer a fixed CPU on
  every host (zeros off x86_64 send the C runtime's maths down its x87
  path, an unported address), game paths need case-insensitive lookups
  off Windows, and Apple silicon has 16 KB pages.
- Portable replacements: winit (window), gilrs or evdev (pads), cpal
  (sound), libloading with `libsteam_api.so`/`.dylib` (Steam: callback
  structs are packed to 4 there, and `CCallbackBase`'s two `Run`
  overloads swap places in the vtable), `directories`. On Linux the
  documents folder is the Proton prefix of app 359870, so saves stay
  shared with `FFX.exe`.

## Graphics

What the game uses: 2,515 distinct shaders in `shaders/d3d11/*.phyre`
(2,024 `ps_4_0`, 491 `vs_4_0`) and 79 inside `FFX.exe`; no geometry,
tessellation or compute shaders; `Texture2D`, `TextureCube`,
`Texture2DMS` (the MSAA setting); BC1, BC3, RGBA8 and D24S8; alpha to
coverage on single-sampled targets. `cargo run --release -p ffx-dxbc
--example census -- <game dir>` prints the shader side.

The draw-stream gate compares the calls `ffx-host`'s layer records before
any back end sees them, so it doesn't depend on the back end or the OS.
Pixel gates compare with the original on the same GPU, as PC2's own
references already do.

Recommended (to be confirmed by the user): a wgpu back end behind
`ffx-host`'s `Backend` trait, with `crates/ffx-dxbc`'s DXBC-to-WGSL
translator (all game shaders translate and pass naga's validation;
`tests/game_shaders.rs`). Considered: Vulkan directly through `ash` with
SPIR-V written by the translator (more control, about twice the work,
macOS then needs MoltenVK), and keeping D3D11 under Proton/DXVK (no work
on Linux, not measured yet, no good macOS path). Proton stays the way to
play on Linux until the wgpu back end passes its gates; D3D11 stays the
Windows default.

## Proof of concept

`tools/m6/wgpu-parity.py` replays full-mode frame captures of the
original (D3D11) through `ffx-render replay` on wgpu and compares every
render target the original dumped, pixel by pixel. Draws whose input the
capture lacks (dynamic buffers the game wrote before the capture was
armed: `crates/ffx-render/examples/capture_gaps.rs`) and what is made
from them are left out.

```bash
cargo build --release -p ffx-render --bin ffx-render --example capture_gaps
python3 -I tools/m6/wgpu-parity.py <capture dir> <work dir>              # Linux (lavapipe here)
tools/build-renderer.sh --bin ffx-render                                    # the Windows build, no game
python3 -I tools/m6/wgpu-parity.py --backend vulkan \
    --exe target/x86_64-pc-windows-msvc/release/ffx-render.exe <capture dir> <work dir>
```

Scene passes on the main machine's GPU (Intel Arc Pro 140T), against
D3D11 on the same GPU:

| Capture (draws) | wgpu on Vulkan | wgpu on D3D12 |
|---|---|---|
| cdsp0000 (128) | 0 px differ | 41 px |
| chars-cdsp0000 (128) | 0 px | |
| bsil0300 (94) | 0 px | 1,962 px |
| kami0100 (139) | 12 px | 32 px |

lavapipe (Mesa's CPU Vulkan) differs by one step in 37-62 % of the
pixels: another GPU, as expected.

The PoC found that D3D11 applies alpha to coverage on single-sampled
targets as a test at 0.5, which wgpu can't state (it allows alpha to
coverage only with multisampling). Without it the prerendered
backgrounds' transparent texels wrote depth and hid kami0100's book (10.8
% of pixels). The replay now discards below 0.5 in the pixel shader for
those pipelines.

Not covered yet: the post-processing passes (the old captures lack their
vertex buffers; captures from `ffx-host --gfx-out` keep every buffer) and
bsil0000 (the hook's captures key objects by address, and a reused
address turns a view into a depth view).

## The wgpu back end

Since 2026-11-28 `ffx-host` has the back end itself (`src/gfx/wgpu.rs`,
`FFX_HOST_GFX=wgpu`; docs/host.md, "The wgpu back end"): the game's
D3D11 calls, live, on wgpu, the default of the native platforms off
Windows. Pixel parity is measured on back-end traces: one run of the
Linux `ffx-rust` on the null device records every back-end call
(`FFX_HOST_GFX_TRACE`), and `tools/m6/host-parity.py` replays the trace on
the Windows GPU into D3D11 and into wgpu, offscreen, and compares the back
buffers at the same presents. Unlike the proof of concept this covers
whole frames: post-processing, Iggy's screens, the 2D passes.

Intel Arc Pro 140T (the main machine), against D3D11 on the same GPU,
2026-11-28, a picture every 25 presents (the boot every 100):

| Trace (presents, pictures) | wgpu on Vulkan | wgpu on D3D12 |
|---|---|---|
| boot: logos, opening, title (1,673, 16) | 136 px of 33.2 M (0.0004 %) | 9,292 px (0.028 %), 237 > 2 steps |
| kami0100 (383, 15) | 0 px | 74 px (0.0002 %) |
| cdsp0000 (376, 15) | 15 px, all 1 step | 1,245 px (0.004 %) |
| menu on the deck (452, 18) | 2 px | 716 px (0.002 %) |
| bsil0000 to bsil0300 (891, 35) | 67 px (0.0001 %) | 63,056 px (0.087 %), 543 > 2 steps |
| battle on the deck (397, 15) | 150,603 px (0.48 %), 5,435 > 2 steps | 955 px (0.003 %) |

The logo, opening, title, kami0100 frames are bit-exact on Vulkan; the
few Vulkan pixels elsewhere are single pixels along thin geometry. The
underwater battle differs on Vulkan only, in a screen-wide grid of
mostly 1-2 steps from its first battle frame: not the depth format
(D3D12 with 32-bit depth still matches D3D11 to 0.003 %), likely the
Vulkan driver's texture filtering in the underwater effect (open). D3D12's
differences are mostly 1 step, its shader compiler's rounding. No back
end reported a problem or a validation error on any trace. Replay time
for the boot's 1,673 frames: D3D11 8-12 s, wgpu 25-30 s (pipeline and
shader compilation included).

Headless on Linux (lavapipe, `FFX_HOST_WGPU_ADAPTER=llvmpipe`) the boot
replay reaches the title with no validation error.


## The Steam Deck

M6 runs on the user's Steam Deck through Proton: first the original
(`FFX.exe`, the hook's replacements off) for the Linux pixel references
(M6-0's baseline), then `ffx-rust.exe` and `FFX.exe` with the
replacements, compared against them; later the Deck checks of M6-7.
`tools/deck/` drives the Deck over SSH from this machine. The harness, the
replay scripts and the comparisons stay here; only the games run there.

### What the user sets up (once)

1. Switch to Desktop Mode (Steam button, Power, Switch to Desktop) and
   open Konsole.
2. `passwd`: SteamOS's user `deck` has no password until one is set, and
   `sudo` and the first SSH login need one.
3. `sudo systemctl enable --now sshd`: the SSH server, now and after
   every boot.
4. Our key: `ssh-copy-id -i ~/.ssh/id_ffx_deck.pub deck@<ip>` from this
   machine (asks for the password once), or append that `.pub` line to the
   Deck's `~/.ssh/authorized_keys` (folder mode 700, file 600).
5. The IP address: Settings, Internet, the connected network (or
   `ip -4 addr` in Konsole). A fixed address for the Deck in the router's
   DHCP settings keeps it from changing.
6. The game installed from Steam, and a Proton installed (Steam installs
   one when a Windows game is first started; else Library, Tools, "Proton
   9.0" or "Proton Experimental"). Proton 9 and later bring the Steam
   Linux Runtime (sniper) with them.
7. While runs go on: the Deck awake and plugged in (a sleeping Deck has no
   SSH). Desktop Mode or Game Mode both work.

The coordinator then writes the address into `~/ffx-work/deck/deck.env`
(never in git): `DECK_HOST=<ip>`. `tools/deck/deck.env` lists every other
setting with its default.

### Safety rules

- Everything of ours lives in `~/ffx-deck` on the Deck (`DECK_WORK`):
  the instances, our Proton prefix, the homes (Documents folders), the
  runs, the logs. The scripts write nowhere else; their copies and folders
  refuse paths outside it.
- The game folder is only read. An instance is the game folder linked into
  `~/ffx-deck/instances/<n>` (hard links on the same filesystem, symbolic
  links when the library is on the SD card), without the user's `mods/`,
  logs, `steam_appid.txt` or any `dinput8.dll`; our programs are copied in
  after the old link is removed, never written through it.
- Our own prefix, `~/ffx-deck/compatdata` (`STEAM_COMPAT_DATA_PATH`), never
  app 359870's `steamapps/compatdata/359870`, which holds the user's saves
  and settings. Every game gets a Documents folder of ours
  (`FFX_HARNESS_HOME`: a copy of this machine's sandbox home with its
  saves), so the user's saves and settings on the Deck are not even read.
- Steam is kept out: Proton gets an empty folder as the Steam client
  (`STEAM_COMPAT_CLIENT_INSTALL_PATH`), so no `steamclient` lands in our
  prefix; `SteamAppId` and `SteamGameId` are unset and `FFX_NO_STEAM=1`
  is set. No run reaches the user's account. `DECK_STEAM=1` lifts this, for
  M6-7's achievement checks only.
- No sound: the games play into a null sink of ours (`PULSE_SINK`,
  removed by `deck-stop.sh`). `DECK_SOUND=1` only when testing sound.
- Nothing in the foreground: by default the game draws into a nested
  gamescope with the headless back end (no output), when the Deck's
  gamescope has one (`deck-check.sh` says); `DECK_DISPLAY=session` puts
  the window on the running session's display, only with the user's OK.
- Never while the user plays: a start is refused (exit 4) while a `reaper`
  process runs (Steam starts every game under one). `DECK_FORCE=1`
  overrides it.
- Low priority: `nice -n 19` and the idle IO class.

### Commands

```bash
tools/deck/deck-check.sh                     # reachable? SteamOS, disk, GPU, session, Protons, the game, ours
tools/deck/deck-install.sh                   # build, copy ffx-rust.exe, ffx-launch.exe, DINPUT8.dll, steam_api64.dll, ffx.sym; instance 0, the prefix
tools/deck/deck-install.sh --from DIR        # the same files from DIR (a release package), no build
tools/deck/deck-replays.sh --record          # the original under Proton, twice: the Deck's references
FFX_HARNESS_EXE=rust tools/deck/deck-replays.sh            # ffx-rust.exe against them
tools/deck/deck-replays.sh                   # FFX.exe with the hook's replacements against them
tools/deck/deck-replays.sh --extra [--record] [replay...]  # run-all.sh's other lists, named replays
tools/deck/deck-replays.sh --audio [--record]
tools/deck/deck-run.sh --rust                # one game by hand (run-game.sh's options; --harness PORT forwards the port)
tools/deck/deck-stop.sh [--status]           # end our games, remove the null sink, close the SSH connection
tools/deck/deck-selftest.sh                  # the scripts against a stand-in Deck on this machine
DECK_DRY_RUN=1 tools/deck/<script> ...       # print every SSH call, copy, forward and start; nothing runs
```

The Deck's references live here, apart from Windows's:
`~/ffx-work/deck/replay-shots-nrt`, `replay-shots-extra-nrt` and
`replay-audio`; each run in `~/ffx-work/deck/runs/<id>`.

### How it works

`deck-replays.sh` runs the harness's `replay` here with
`FFX_HARNESS_LAUNCHER=tools/deck/deck-run.sh` (`docs/harness.md`,
"Parallel games"), a one-slot pool of its own (`~/ffx-work/deck/game-slot`)
and port 27300 (`DECK_HARNESS_PORT`, apart from this machine's 27100 + n).
`Game::launch` prepares the sandbox home here as for any replay and calls
`deck-run.sh` with `run-game.sh`'s options. That copies the home to
`~/ffx-deck/homes/<n>`, refreshes the instance, starts the game detached
on the Deck, and forwards 127.0.0.1:27300 here to the Deck's
127.0.0.1:27300 through the SSH master connection (`ssh -O forward`). The
harness then talks to the game as it does on Windows. The trace path
handed to the game is a Deck path in Windows form
(`Z:\home\deck\ffx-deck\runs\...`: Proton's prefixes map drive Z: to
`/`), so traces, screenshots and audio captures are written on the Deck,
one folder per replay, and copied back after it (tar over SSH; the Deck
needs nothing but tar). `run-all.sh` with `FFX_REPLAY_COMPARE_ONLY` then
compares them with the Deck's references as it compares local runs
(`--record` stores them). The scripts send `tools/deck/remote.sh` over SSH
on stdin for every call; nothing of ours is installed on the Deck outside
`~/ffx-deck`.

A start on the Deck, as `remote.sh` builds it:

```
cd ~/ffx-deck/instances/<n>
env -u SteamAppId -u SteamGameId ... FFX_DECK_RUN=1 \
    STEAM_COMPAT_DATA_PATH=~/ffx-deck/compatdata STEAM_COMPAT_CLIENT_INSTALL_PATH=~/ffx-deck/no-steam-client \
    STEAM_COMPAT_INSTALL_PATH=<instance> STEAM_COMPAT_LIBRARY_PATHS=<libraries> FFX_NO_STEAM=1 \
    PULSE_SINK=ffx_deck_null FFX_HARNESS=<port> FFX_HARNESS_HOME='Z:\...\homes\<n>' [WINEDLLOVERRIDES=dinput8=n,b] ... \
  nice -n 19 ionice -c 3 [gamescope --backend headless -w 1280 -h 720 -W 1280 -H 720 --] \
    [<library>/steamapps/common/SteamLinuxRuntime_sniper/_v2-entry-point --verb=waitforexitandrun --] \
    '<Proton>/proton' waitforexitandrun ffx-rust.exe | FFX.exe | ffx-launch.exe FFX.exe
```

- Proton: `DECK_PROTON` (a name or a folder), else the newest numbered
  "Proton N.N" under the libraries' `steamapps/common`. Steam's own choice
  for app 359870 (`config.vdf`'s CompatToolMapping) is printed by
  `deck-check.sh`; set `DECK_PROTON` to it for the baseline. The library
  holding the game is found through `steamapps/libraryfolders.vdf` and
  the library's `appmanifest_359870.acf` (`installdir`), never a fixed
  path.
- The runtime container: when the Proton's `toolmanifest.vdf` asks for
  `require_tool_appid` 1628350 (sniper) or 1391110 (soldier) and that
  runtime is installed, the start goes through its `_v2-entry-point
  --verb=waitforexitandrun --`, the chain Steam itself uses for Proton
  games (`DECK_SLR=0` calls the proton script directly).
- The hook: Wine uses its own `dinput8` unless told otherwise, so FFX.exe
  runs get `WINEDLLOVERRIDES=dinput8=n,b` (the folder's `DINPUT8.dll`
  first); `--no-hooks` gets `dinput8=b`, so nothing needs removing.
- Fixed addresses (`--virtual-clock`): through `ffx-launch.exe FFX.exe` as
  on Windows (`DECK_FIXED=direct` starts `FFX.exe` itself).
- `deck-install.sh` makes the prefix with `proton getcompatpath
  ~/ffx-deck`, which sets the prefix up and answers with the folder's
  Windows path: a check of the Z: mapping every path above relies on.

Facts from Valve's `proton` script (the Proton repository, branch
`proton_9.0`, read for its interface only): the verbs `run`,
`waitforexitandrun` (waits for the prefix's wineserver to end first),
`runinprefix`, `getcompatpath`, `getnativepath`, `destroyprefix`;
`STEAM_COMPAT_DATA_PATH` is required (it stops without it) and
`STEAM_COMPAT_CLIENT_INSTALL_PATH` too (a Python error without it, for
every verb but `runinprefix`); the prefix is `$STEAM_COMPAT_DATA_PATH/pfx`
with `z:` linked to `/`; programs start through Proton's builtin
`steam.exe`; the Steam client's `legacycompat` `steamclient` DLLs are
copied into the prefix from `STEAM_COMPAT_CLIENT_INSTALL_PATH` when they
are there; a `WINEDLLOVERRIDES` from the environment comes before
Proton's own entries; `SteamAppId` and `SteamGameId` are read, never set;
`PROTON_LOG=1` writes `steam-<SteamGameId>.log` to `PROTON_LOG_DIR` or the
home folder, and only with a `SteamGameId`.

### To be checked on the Deck

`deck-selftest.sh` runs every script against a stand-in Deck here (fake
Steam folders, Protons that record their calls, a fake runtime entry
point): 47 checks, among them the environment and command of every
start, the instances, the refusal while a `reaper` runs, and the game
folder byte for byte unchanged. What only a Deck can answer:

- gamescope's headless back end with DXVK inside it (else
  `DECK_DISPLAY=session` with the user's OK);
- whether Wine accepts `ffx-launch`'s ASLR mitigation policy (else
  `DECK_FIXED=direct`), and whether Wine's addresses repeat between runs
  without it;
- the harness's TCP port under Wine, reached through the forward;
- `pactl` and the null sink under SteamOS's PipeWire;
- the display variables read from the Steam client (Game Mode) or
  Plasma (Desktop Mode) for `DECK_DISPLAY=session`;
- the first start's time (a new prefix: `FFX_HARNESS_STARTUP`, 600 s for
  Deck replays);
- the replays' timing on the Deck's CPU (`FFX_REPLAY_TIMEOUT`).
