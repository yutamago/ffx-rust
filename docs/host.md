# ffx-host and ffx-rust.exe

`ffx-rust.exe` runs FFX without loading `FFX.exe` (M5 stages 3 and 4,
`docs/rewrite-plan.md`). It maps the player's own `FFX.exe` as data, runs
the ports from one function table, and, during development only, runs every
function that has no port yet from `FFX.exe`'s `.text` in Unicorn, on the
same memory. The release runs no `FFX.exe` code.

## The arena

Every game address is a `u32` offset from `Arena::base`. The bridges'
`Mem` reads and writes through it, so a port runs unchanged on any target.

| | x86_64 (stage 4) | i686 (stage 3) |
|---|---|---|
| base | one 4 GB reservation (`mmap PROT_NONE` / `VirtualAlloc MEM_RESERVE`) | 0: the process's own address space |
| a region | committed inside the reservation (`mprotect` / `MEM_COMMIT`) | `VirtualAlloc` at its game address; refused if the address is taken |
| game address = host pointer | no: `base + addr` | yes |

Regions (`Arena::regions`):

| Region | Where |
|---|---|
| `FFX.exe` (headers and every section) | `0x00400000`–`0x0277d000`, its preferred base, so every `ffx.sym` address is its own game address and nothing is relocated |
| main stack (2 MB), stub page, thread block (GDT, TEB, PEB, TLS slots) | the first free gaps above `0x03000000` |
| heap (512 MB, the C runtime's and `HeapAlloc`) | the first gap above `0x10000000` |
| `VirtualAlloc` regions | the first free gaps above `0x03000000` |

Regions are 64 KB aligned, Windows' allocation granularity. Pages outside
every region stay unmapped: Unicorn reports an access there as
`BadAccess`, and `ArenaMem` reads zeros, drops the write and counts it
(the report lists the first ones).

On i686 `ffx-rust.exe` must leave `0x00400000`–`0x0277d000` free. It
links at `/BASE:0x70000000`, and `main` reserves the range first thing
(`arena::reserve_image_range`; the image's regions are then committed
inside that reservation). That is not enough: Windows creates the main
thread's stack and the first heaps at the lowest free addresses before
any of the program's code runs, and on the first launch the stack's 1 MB
reservation sat at `0x00400000` (`VirtualQuery`: `MEM_RESERVE`,
`MEM_PRIVATE`, allocation base `0x00400000`). So when the reservation
fails, `ffx-rust.exe` starts itself again (`src/relaunch.rs`): suspended,
with bottom-up ASLR off (as `ffx-launch` does for `FFX.exe`), reserves the
range in the child with `VirtualAllocEx` while nothing in it has run,
resumes it with `FFX_HOST_IMAGE_RESERVED=1` (the child adopts the
reservation after checking it with `VirtualQuery`), waits for it and
exits with its code. The child is in a job that ends it when the parent
goes. A child whose range is taken anyway would be ended and another
started (8 tries); every launch so far got it on the first.

The release maps only the data sections (`.rdata`, `.data`, `.rodata`,
`_RDATA`, `.rsrc`). This build maps `.text` too, read as data, for Unicorn.

## The function table

`Table` maps an original address to an `Entry`: name, convention, stack
words, and the port, `fn(&mut Exec, &Args) -> Ret`. `Args` holds `ecx`,
`edx`, the stack words and the address of the first one (`slots`, for
originals that write their own argument slots). `Ret` says where the
result goes: `eax`, `edx:eax`, `ST0`, or nothing (the caller keeps its
registers, as the hook's thunks keep them).

Everything that calls code goes through the table:

- Unicorn code reaching a ported address: the address holds `int3` in the
  arena's copy of `.text`, and the executor runs the port;
- a port calling an address (`call_sym`, `call_virtual`, a stored function
  pointer): `Exec::call` takes the port when there is one, the import's
  Rust side for an import stub, else Unicorn;
- later, a mod replaces an entry by address.

### One source of truth

The ports are the hook's `ported!` lists (`crates/ffx-hook/src/ported/*.rs`,
15,157 entries on 2026-10-29). `ffx-host-ports` compiles those same files
a second time (`#[path]` to `crates/ffx-hook/src/ported/mod.rs`, with
`cfg(ffx_host)` set by its build script), so there is no second list:

- `ported!` (the `cfg(ffx_host)` arm in `ported/mod.rs`) makes each shim a
  plain Rust function and each line a `Hook`: `$addr`,
  `stringify!($name)`, the convention from the ABI string, the stack
  words (`stack_words`, the hook's own), and an adapter `fn(&Args) -> Ret`
  that decodes the caller's words into the shim's typed arguments
  (`FromWords`: register arguments first, one word for `u32`/`i32`/`u8`/
  `u16`/`bool`/`f32`, two for `u64`/`f64`; `slots` from `Args::slots`) and
  encodes the result (`IntoRet`: integers to `eax`, 64-bit to `edx:eax`,
  floats to `ST0`, `()` to nothing, as the thunks' `Saved` keeps the rest).
  The input syntax is unchanged, so new lines need nothing;
- `mem()` is `RawMem` at the preferred image base; on 64-bit hosts
  `RawMem` reads and writes through the router (the arena);
- `StackFrame` is carved from the game thread's stack in the arena
  (`Router::frame_alloc`, released on drop), the hosts' scratch
  (`callee_scratch`, `scratch`) are per-thread blocks in the arena
  (`Router::scratch`);
- the crate-root names the shims use (`crate::rebase`, `crate::log`,
  `crate::harness`, `crate::iggy_log`, `crate::loader_turn`,
  `crate::hook_only`) are `ffx-host-ports`' own: identity rebase, stderr,
  and no harness hooks yet.

**The call router** (`ffx_bridge::route`). Every call from Rust into game
code goes through it: the hook's `call_cdecl*`, `call_thiscall`, `call0`,
the former 61 `transmute` call sites and 22 x87 `asm!` blocks in the shims
(`route::cdecl/stdcall/thiscall/fastcall/caller_pops/x87`), and the
`RawMem` impls of `ffx_bridge::Host`, `ffx_graphic::host::Host` and
`ffx_script`'s `NativeHost`. With no router on the thread (the hooked game)
it calls natively, the same words, convention and result width as before;
in `ffx-host` the executor is the thread's `Router` while a routed port
runs (`Exec::run_port`), and the call goes to `Exec::call` (the table, an
import's Rust side, else Unicorn). `route::x87` loads its operands on
Unicorn's x87 stack through a small stub and calls the intrinsic's thunk
or import slot there. `tools/check-ported.py` rejects any other way to call
the game from `ported/*.rs`; check-callconv and check-thisarg know the
route calls.

Two rules make routed ports behave like the hooked game's (found merging
the table with the multi-threaded boot, 2026-10-29):

- **A call from Rust puts its words on the game stack.** When a port
  calls another port (`Exec::call` with `Args::slots` 0), the words are
  written below the current frame first, with a return-address word, and
  the callee gets their address as its `slots`, as a call from the game
  would. Without it `Phyre_PhyrePrintf`'s `va_list` (`slots + 8`) read
  address 8: the loader thread faulted inside `_vsnprintf` and the boot
  never presented a frame.
- **A halted thread unwinds its routed ports.** A port can't see a stop:
  its calls just return 0, and a port that polls in a loop spins forever
  after the budget or a failure. Once the thread is halted, the router
  unwinds the port (`resume_unwind` with a private payload that
  `Exec::run_port` catches), and the caller sees the stop as for any other
  call. A real panic in a port ends the thread with `port <name>
  panicked`.

**Held shims.** A shim that hands the game a Rust local's address
(`&raw mut x`, `buf.as_mut_ptr()`, a `thread_local!`'s) can't run from
the table: on x86_64 that address is outside the arena, and even on i686
Unicorn doesn't map the host stack. `tools/host-ports.py` lists them
(their bodies, or same-file helpers and `macro_rules!` macros they name,
transitively) in `crates/ffx-host-ports/src/held.rs`; they stay out of the
table and their originals run in Unicorn. 305 on 2026-10-29: each becomes
portable when its local becomes a `StackFrame`. Rerun the tool after
merging `ported!` lines; check-ported fails while the list is stale.

The tool missed one until host-battle (2026-10-29): battle.rs's
`regist_signal`, which every shim using its `script!` macro reaches
(`MsSetMotion`, `MsAtelRequestExe` and 105 more), handed
`AtelRegistSignal2` a Rust array's address. The tool read neither macro
bodies nor helpers with an array parameter (`[u32; 8]`'s `;` made it take
the function for a declaration). In ffx-rust.exe that address (the
host pointer's low 32 bits, an arena offset) held no signal block, so no
battle script request was ever queued (blocker 7). The
helper now builds the block in a `StackFrame`, and the tool follows macros.

## Rust and Unicorn

Unicorn maps every arena region with `mem_map_ptr` on the arena's own host
memory, so the ports and the original code share one memory, page for
page. Nothing runs inside a Unicorn hook except bookkeeping: an `int3`
stops the emulator, and the executor's loop decides.

- **Unicorn → Rust.** The `int3` at a ported address stops the emulator at
  the callee's entry (`esp` at the return address). The executor reads the
  entry's stack words, saves every general register, runs the port,
  restores them, applies `Ret`, and resumes at a return stub in the stub
  page: `ret 4n` for a callee-pops convention (stdcall, thiscall, fastcall)
  with `n` stack words, `ret` for cdecl and `fastcall-caller-pops`, and
  `fld qword [cell]; ret 4n` for a float result (the value is the port's
  `f64`, which the game's 53-bit x87 holds exactly). Saving and restoring
  `eax`, `ecx` and `edx` keeps what the LTCG callers expect: MSVC's
  whole-program optimisation lets a caller keep those live across a call it
  knows leaves them alone (`docs/hooking.md`, the thunks).
- **Rust → Unicorn.** `Exec::call` pushes the stack words below the
  current `esp` (a port runs between an original's call and its return, so
  that frame stays intact), pushes the sentinel (an `int3` in the stub page)
  as the return address, sets `ecx`/`edx` by the convention, empties the
  x87 stack, and runs until the sentinel. Then it reads `eax`, `edx` and
  `ST0`, and restores the registers it saved. Calls nest as plain Rust
  recursion; the innermost sentinel return belongs to the innermost call.
- **Conventions.** `Conv` is cdecl, stdcall, thiscall (`this` in `ecx`),
  fastcall (`ecx`, `edx`) and `FastcallCallerPops`, the LTCG custom
  convention (`ecx`, `edx`, stack words the caller pops: `ret`, then the
  caller's `add esp`). `Conv::callee_pops` picks the return stub.
- **Failures.** An unstubbed import, or a fault or exception no frame
  handles (below, "Exceptions"), ends the thread, on the
  main thread the whole run (`Exec::end`; a milestone or the budget end the
  run from any thread): every level returns `Error::Stopped`, since callers
  such as `_initterm` or a port can't all carry a `Result`. The outcome
  says where (`Stop::Failed(why, eip)`, the caller of an unstubbed import),
  the report adds the return addresses found on the stack, and
  `FFX_HOST_TRACE=n` the last `n` basic blocks.
- **x87.** The control word starts at `0x027f` (53-bit), as Windows starts
  threads. The transcendental instructions run exactly (below, "x87").

## x87

Unicorn (QEMU) computes `fsin`, `fcos`, `fsincos`, `fptan`, `fpatan`,
`f2xm1`, `fyl2x`, `fyl2xp1`, `fprem` and `fprem1` through host `double`
functions: 11 bits of the 64-bit mantissa are lost and `fprem`'s remainder
loses its sign, so MSVCR110's maths (which runs on them; `pow(3, 4)` came
out `81.00000000000003`) is wrong in the last bits. `ffx-fpu` (the oracle's
module, now a crate both use) computes them as an Intel FPU does: 320-bit
arithmetic rounded to the 64-bit mantissa in the control word's rounding
mode, the FPU's 66-bit pi for the argument reduction, `fprem` exact.

- **Where.** `ffx_fpu::sites` lists them per module from the PE header's
  `TimeDateStamp` and `CheckSum`: the player's `MSVCR110.dll`
  (11.0.51106.1) has 22, at RVAs from a linear disassembly; its
  `MSVCP110.dll` and `FFX.exe` have none (22 and 798 `0xd9 xx` byte pairs
  in `.text`, none an instruction start: the game's own maths calls the
  runtime or uses SSE). A module of another build gets every possible
  pair, watched by a code hook each (a hook fires only where an
  instruction really starts; slower, never patched).
- **How.** The known sites hold `int3` in the arena; the executor's
  interrupt hook computes the instruction on the emulator's registers
  (`ffx_fpu::unicorn::step`: `ST0`/`ST1`, the stack top and tags, the
  condition codes and flags) and the emulator goes on after it, without
  stopping. The report counts them ("exact x87 instructions").
- **Checked.** `tests/x87.rs` runs the 1,327 recorded cases of
  `ffx-oracle`'s `tests/data/msvcr110-math.tsv` (the cdecl maths exports,
  the `_CI*` intrinsics and the `_libm_sse2_*_precise` ones, recorded from
  the same DLL on an Intel CPU at control word `0x027f`) through the
  player's DLL in `ffx-host`: all match, bit for bit, NaNs included.

## Exceptions

Emulated code throws and catches as on 32-bit Windows (`src/exec/seh.rs`):

- **Dispatch.** `RaiseException` (a C++ `throw` is MSVCR110's
  `_CxxThrowException` → `RaiseException(0xe06d7363, ...)`) and faults
  (access violation `0xc0000005` with its read/write/execute and
  address, division by zero, illegal instruction, a stray `int3`) write an
  `EXCEPTION_RECORD`, a `CONTEXT` and a dispatcher context below the
  stack and call each handler on the thread's `fs:[0]` chain,
  `handler(record, frame, context, dispatcher context)`, as
  `RtlDispatchException` does: `ExceptionContinueSearch` goes to the next
  frame, `ExceptionContinueExecution` loads the registers (and the x87
  state) from the `CONTEXT`, `ExceptionNestedException` marks the record
  nested until past the frame it names.
- **In the executor's loop, not in Rust.** A handler is entered with a
  return address in the thread's stub page (an `int3`), so a handler that
  never returns (a catch: MSVCR110's `_JumpToContinuation` goes on in the
  catching function) just goes on, at no cost to the host stack. Each
  call is wrapped in a registration of the dispatcher's own, as
  `RtlpExecuteHandler2` does; MSVCR110's catch code relies on it
  (`_UnwindNestedFrames` saves and restores that head, `_JumpToContinuation`
  unlinks it), and its handler reports a nested exception.
- **`RtlUnwind(target, ip, record, value)`** (MSVCR110's import) calls the
  handlers from the head down to `target` with `EXCEPTION_UNWINDING` (and
  `EXCEPTION_EXIT_UNWIND` for 0), each in an unwind registration, unlinks
  each frame, and returns `value` to its caller (x86 ignores `ip`). These
  handlers return (they run destructors and `__finally` blocks), so they
  are called from Rust.
- **Across a Rust port.** When a port called the code that threw and the
  catch is in a frame older than the port, the catching function returns
  to an outer level's sentinel (`esp` tells which: each Rust → Unicorn
  call records the `esp` its sentinel return leaves). Every Rust level in
  between unwinds (`Exec::call` returns `Error::Stopped` to the port,
  whose further calls do nothing), and the outer level returns as if its
  own call had, with the registers the sentinel return left: the port's
  frame is abandoned, as an unwind abandons a frame without handlers.
  Ports hold no destructors that need to run, so nothing is lost.
- **Unhandled.** At the chain's end (no frame took it), or when the C
  runtime gives up on it (`UnhandledExceptionFilter`, which its start-up's
  `__except` and `terminate` call), the thread ends, on the main thread the
  run: `Stop::Failed` names the exception, for a C++ one its type from the
  throw information (`unhandled C++ exception std::bad_alloc`), with the
  `eip` of the throw or fault, the return addresses on the stack and the
  last blocks (`FFX_HOST_TRACE`). The report counts the exceptions
  dispatched.
- **Checked.** `tests/seh.rs` builds MSVC-shaped frames (an EH
  registration, `__CxxFrameHandler3` tables: unwind map, try block, catch
  handlers) and throws an `int` through the player's MSVCR110: caught
  across `FFX.exe`'s `FUN_00948c30` (`call [ebp+8]`), the try block's
  object destroyed by the unwind, the chain empty after; a `catch (...)`
  that rethrows (`throw;`) to an outer catch; the same catch across a Rust
  port in `FUN_00948c30`'s place (the port's frame abandoned, the
  catching function's tail run once); an access violation handled by an
  SEH handler that fixes the `CONTEXT` and continues; an unhandled throw
  ending the run with its report.
- **Not done.** Collided unwinds (an unwind started inside an unwind
  handler that reaches the outer one) go on as a plain continue; the
  vectored handlers (`AddVectoredExceptionHandler`) don't exist; a
  thread's top frame is the chain's end, not Windows' `BaseThreadInitThunk`
  filter (the same report either way); faults inside the Rust side
  (`ArenaMem`'s dropped writes) are not exceptions.

## Imports

`FFX.exe` imports 536 functions from 19 DLLs (MSVCR110 188, KERNEL32 112,
MSVCP110 75, USER32 41, iggy_w32 41, fmodex 23, fmod_event 17, steam_api 9,
ADVAPI32 7, the rest under 5 each). Each IAT slot points at its own `int3`
in the stub page; the four data imports (`_acmdln`, `_fmode`, `_commode`,
`_HUGE`) point at cells instead. `imports::TABLE` gives each import's
convention, stack words and Rust side.

- **C runtime and STL: the player's DLLs, some Rust.** See "The C runtime
  DLLs" below: `FFX.exe`'s `MSVCR110` and `MSVCP110` imports go to the
  player's own DLLs in Unicorn, except the 26 whose Rust side is exact
  (`RUST_WITH_DLLS`). `--no-dlls` runs the Rust side only, as the first
  round did (the run then stops at `MSVCP110.dll!basic_ios`); `--lenient`
  lets unstubbed `MSVCR110` functions (cdecl, so nothing to pop) return 0
  and only lists them.
- **Win32.** The stand-ins are deterministic and platform-free, so the
  Linux check runs them (fixed clocks, fake handles, files from the game
  folder through `std::fs`, read-only). On Windows the window, message,
  cursor and timer calls forward to the real API (below, "Windows"); the
  files already are the real game folder through `std::fs` on either
  side (`src/files.rs`).
- **D3D11, DXGI, DirectInput.** COM objects in the arena, a back end
  behind them: below, "D3D11 and DXGI".
- **FMOD, Iggy, movies, Steam.** FMOD on the Rust mixer (below,
  "FMOD"), Iggy on the layer of `src/iggy.rs` and `ffx-swf` (below,
  "Iggy"); `ffx-movie` and `steam_api.dll` (`steam_api64.dll` at stage 4)
  later. Steam is absent for now (`SteamAPI_RestartAppIfNecessary` and
  `SteamAPI_Init` return false, so `Steam_Init` skips the interfaces and
  achievements); Iggy exports without a Rust side are null stand-ins that
  return 0 (their stack size comes from the decorated name,
  `_IggyInit@4`).
- **The window.** Linux: `CreateWindowExA` returns a fake handle and
  records a milestone; `ShowWindow`, `SetWindowPos`, `GetClientRect`
  (1920 x 1080), `PeekMessage` (no messages) and the rest of the window
  calls on the way to the device are stand-ins. Windows: real (below,
  "Windows").
- **Milestones.** The renderer's start-up first calls `D3D11CreateDevice`
  for the feature level only (no device, no context): `S_OK` and 11_0,
  recorded. `D3D11CreateDeviceAndSwapChain` makes the layer's device and
  swap chain (recorded with the back end and the size); `--presents N`
  ends the run at the `N`-th `Present`, `--stop-at DLL!name` at any
  import, the window included.
- **Past the device** (`src/crypt.rs`, `src/stand_ins.rs`): the file
  system's MD5 of every path through `CryptAcquireContextA`,
  `CryptCreateHash(CALG_MD5)`, `CryptHashData` and `CryptGetHashParam`
  (exact: `md-5`); `wsprintfA/W` (USER32's formatter, no floats);
  `GetSystemTime` (the fixed clock of `GetSystemTimeAsFileTime`);
  `AreFileApisANSI`. `RaiseException(0x406d1388)` (MSVC's thread-naming
  exception) returns: the game's filter at `0x0043015c` answers
  `EXCEPTION_CONTINUE_EXECUTION`, so without a debugger that is what
  happens.

## D3D11 and DXGI

`D3D11CreateDeviceAndSwapChain` (`PRendererD3D11_createDeviceAndSwapChain_00595800`)
creates the layer (`src/gfx.rs`): the device, its immediate context, the
swap chain and its back buffer; the DXGI factory, adapter, output and
device, and the DirectInput objects, are made when the game first asks
for them.

**Objects.** An interface pointer the game holds is a 16-byte block on
the arena heap whose first word is its class's vtable, also in the arena
(`src/com.rs`). Each vtable slot points at its own `int3` in a 64 KB stub
region, and each `int3` is a trap (`exec::Trap`, `Shared::add_trap`): the
executor runs it like an import, with the method's stack words (`this`
first), and returns through `ret 4n`. Emulated code calling
`(*obj)->Method(...)` and a port's `Exec::call` on a vtable entry land in
the same place. So a COM object is a `u32` handle whatever the host's
pointer width, and nothing of the host's objects is in the arena.

The vtables come from `src/com_methods.rs`, generated by
`tools/host-com-methods.py` from the `windows` crate's `*_Vtbl` structs
(declaration order of `d3d11.h`, `dxgi.h`, `dinput.h`; every argument of
these methods is one word on i686, two for a `u64`): 29 classes,
`ID3D11Device1` (50 slots), `ID3D11DeviceContext1` (134), the resources,
views, shaders, layouts, states and queries, `IDXGISwapChain`,
`IDXGIFactory1`, `IDXGIAdapter1`, `IDXGIOutput`, `IDXGIDevice1`,
`IDirectInput8A`, `IDirectInputDevice8A`. `QueryInterface` answers the
interfaces a class's vtable declares (its chain) and `IDXGIDevice` for
the device, by the IIDs in the same file; `ID3D11Debug` and
`ID3D11InfoQueue` (the game asks for both, `0x00b31450`/`0x00b31460`) get
`E_NOINTERFACE`, as a device created without the debug flag answers.
`AddRef`/`Release` count; a released block is never reused, so a stale
pointer still names its object in the log.

**The layer.** Every method reads its arguments out of the arena,
keeps what the API would know (resource and view descriptions, the
contents of every buffer and of every mappable texture in an arena copy,
which `Map` hands out, the context's bound state), records the call, and
hands the decoded call to the back end (`Backend`: `create`, `op`,
`read`, `query_data`, `present`):

- **`Null`** (Linux, `--gfx-null`): no GPU. Objects are stand-ins, a read
  map gives back what was written, queries are done at once (an event
  query is signalled, timestamps tick 1 ms a query at 1 GHz);
  `CheckFormatSupport` says yes to every usage, `CheckFeatureSupport`
  zeroes (nothing optional), the adapter is "ffx-host null adapter", the
  output one 1920 x 1080 mode at 60 Hz, DirectInput has no devices
  attached.
- **`D3d11`** (Windows, `src/d3d11.rs`): the real device
  (`D3D11CreateDevice`, hardware, 11_0, the game's flags). Descriptions
  are copied into the API's structures, contents passed as slices,
  objects mapped from their handles to the real interfaces. A mapped
  write reaches the resource at `Unmap` (a discarding map of a dynamic
  resource, else `UpdateSubresource`), a mapped read is read back at
  `Map`. No host pointer reaches the game, so it builds the same for
  stage 4. The device is made with its swap chain on the game's (real)
  window, from the game's `DXGI_SWAP_CHAIN_DESC` field by field
  (`D3D11CreateDeviceAndSwapChain`); the back buffer is the swap chain's
  buffer 0 and `Present` presents. A description without a window gets
  the device alone, an offscreen back buffer and a flush for `Present`.
  The harness's `shot` copies the back buffer to a staging texture
  (`Backend::back_buffer_image`).

**The recording.** Whatever the back end, the layer writes the stream the
hook's capture writes (`ffx_gfx`, `docs/drawdiff.md`): `Buffer`,
`Texture` (2D), `View`, `Shader` (vertex and pixel), `Layout` and `State`
messages as the objects are made, `UpdateTexture` for texture updates,
`Release` at a last release, and at each `Present` a `Frame` of draws
(everything bound, constant buffer windows as bytes), clears, texture
copies and `UpdateBuffer`s (the span of a non-constant buffer that
changed since the stream last saw it). Ids are the objects' handles.
`--gfx-out DIR` writes it as `capture.ffxgfx` after `CAPTURE_MAGIC`,
with `calls.txt`: one line per COM call (`present#this
Interface::Method(args) -> result`, `QueryInterface`'s IID by name).
Methods the layer doesn't answer return `E_NOTIMPL` (or nothing) and are
listed in the report (`gfx unhandled`); on the boot so far there are none.

## The clock

`src/clock.rs` applies the hook harness's fast mode, virtual clock and
lockstep rules (docs/harness.md, "Frames and threads", "Load pacing",
"Sound in lockstep", "Flash on the virtual clock"), always on, so a run
advances the same way whatever the host's (or the emulator's) speed:

- **Game time** is `2^20 s` plus the time skipped, never the host's:
  `Phyre_PTimerWin32_GetTime` (`0x0042fd80`, a port returning `ST0`),
  `QueryPerformanceCounter` (10 MHz), `GetTickCount(64)` and `timeGetTime`
  (ms) all read it. Two sleeps move it: the frame limiter's `Sleep`
  (`Game_Main`'s `call [Sleep]` at `0x0062f3bb`, recognised by its return
  address) steps to the next frame's time exactly (start + last frame +
  vsyncs x 1/59.94 s, plus 1e-9 s), and the start-up loop's
  `SleepThreadInMillisecond(33)` (`0x0066b345`, a port of `0x006f2d20`)
  by its milliseconds. Every other sleep is a real one of at most 5 ms
  (the game's sleeps only yield; the clock that times it is virtual) and
  leaves the clock alone.
- **The frame boundary** is the entry of `FFXApplication_animate`
  (`0x0042f520`), wrapped: a port that runs the boundary's work and then
  the original through a trampoline (`Table::wrap`: the original's first
  whole instructions copied into the stub page, then a `jmp` into its
  body; `Exec::call_original`). Where the table already has a port (a
  `ported!` entry: `Phyre_PMutex_lockInner_00431850`, `FmodManager_tick`),
  `Table::wrap` keeps it and `call_original` runs that port instead. The
  clock registers after the `ported!` entries, so its own ports at the
  vsync thread's and `SleepThreadInMillisecond`'s addresses replace
  theirs. Boundary `n` (`n` updates done) runs the
  replay script, the harness (its trace, jobs and lockstep hold:
  `docs/harness.md`, "Two processes"), the loader's turn, the vsyncs,
  FMOD's turn and the harness's `callnext` calls, in that order, as the
  hook's `animate` does.
- **Lockstep** holds from the main loop's first boundary on (before it, the
  start-up loop's loads run free, as before the replays' `lockstep on`).
  Every boundary is a hold: the script decides there and the next update
  runs only then.
- **The loader's turn.** The asset loader
  (`AsyncLoadManager_threadMain_00691360`, wrapped to note its thread)
  takes the render lock (`0x00c94ee4`, through
  `Phyre_PMutex_lockInner_00431850`, wrapped) only in its turn, which the
  boundary gives while the request lists (`g_AsyncLoadManager` `+0x20`,
  `+0x2c`) are not empty and waits out; the render thread (noted by the
  wrapped `Renderer_PresentFlip` `0x00593760`) waits at its next take
  meanwhile. Inside an update the loader waits, unless the main thread
  sleeps (the hook's stall case: `CdReadSync` waiting for a read) or the
  update has run 3 s of host time (the hook's 100 ms, scaled for the
  emulator).
- **FMOD's turn.** `FmodManager_tick` (`0x006fa700`, wrapped) runs once per
  boundary from the first one on, when the main thread gives the turn and
  waits for it; in between it serves the synchronous command the main
  thread waits for (`+0x30` handler into `+0x48`, `+0x44`, `SetEvent(+0x1c)`).
- **Vsync.** `createVsyncEmuThread` (`0x00679e60`) starts no thread; its
  handler runs at the boundary once per vsync of game time
  (`endVsyncEmuThread`, `VsyncEmu_Wake` are ports too). Before the first
  update it runs after each flip.
- **Reads.** `FileSys_SubmitRead` (`0x0061c220`) runs the read and the
  decompression on the calling thread at once.
- **The opening logos** end on their first frame, as in fast mode: after
  each flip `g_PhyreSceneOpeningPlaying` (`0x00ccb9c2`) is cleared.
- **Input.** `Input_KeyHeld` (`0x00629d50`) is wrapped as the harness
  wraps it: the buttons the script holds read as their first keyboard
  binding. DirectInput enumerates a mouse and a keyboard (the game's
  callback `0x00623330` makes its input devices from them; without a
  mouse `IggyMouseQueue_update_00a25ab0` reads through a null device);
  `GetCursorPos` answers the harness's far-off position.

`src/replay.rs` plays a replay script there (`--replay`): `waitfor`,
`shotwhen` (the update the shot shows is noted; the null device has no
image), `press`, `wait`, `pin` (the harness's, the time parts included)
and the no-ops (`lockstep`, `trace`, `realtime`, `settings`,
`audiomark`).

## FMOD

`src/audio.rs` puts FMOD's 40 imports on the Rust mixer, the engine the
hooked game's `FFX_RUST_AUDIO=1` uses (`ffx_sound::replay::Engine`; the
hook's `rust_audio.rs` is its other driver), with the same calls:

- `EventProject` and `EventGroup` are 8-byte blocks on the heap whose
  vtables hold traps (14 and 18 slots; the five the game calls with
  arguments pop them); events, channels and sounds are numbers.
- Files go through the game's own callbacks (`System::setFileSystem`, run
  in Unicorn on the calling thread), so the archive and mods work as with
  FMOD.
- `EventSystem::update` mixes one 1,600-frame block (one FMOD tick: the

  (`SOUNDDEF_END`, `EVENTFINISHED`).
- Output: none (the blocks are counted, the report says how many), or
  `--audio-wav FILE`, the mix in FMOD's WAV writer format as the audio
  gate records it. The device output (WASAPI) is the hook's

## Iggy

`src/iggy.rs` answers Iggy's imports (docs/formats/pc-ui.md, "Iggy
calls"):

- a player is a 0x100-byte heap block (its handle), the movie's bytes
  kept; `IggyPlayerProperties` points at its `+0x40` (width, height and
  frame rate from the SWF header);
- `IggyPlayerCreateFastNameUTF8` gives a non-zero id per name
  (`IggyMenu_callIggyAS3External` loops on `Sleep(5)` until it gets one:
  the null stand-in's 0 hung the boot there);
- `IggyPlayerCallFunctionRS` decodes the `IggyDataValue`s (types 3-6) and
  hands the call to the player; it writes no result (the game never reads
  it, and some of its result buffers are 12 bytes);
- `IggyPlayerReadyToTick` keeps each player's accumulator on the virtual
  clock (ready while it holds a frame period), `TickRS` takes one off;
- `IggyMakeEventNone`/`MouseMove` write the layer's own 24-byte event
  (the game's buffers are 24 bytes: writing more broke
  `IggyMenuManager_dispatchMouse_00a26ce0`'s stack cookie);
- an AS3 `ExternalInterface.call` runs the game's callback
  (`IggySetAS3ExternalFunctionCallbackUTF8`; stdcall(user, player, call),
  the call block built in the arena with the NUL-terminated name the
  callback hashes), and what the game answers through
  `IggyPlayerCallbackResultPath` + `IggyValueSetStringUTF8RS` is the
  result.

With the `swf` feature (`src/iggy/swf.rs`) each player is an
`ffx_swf::stage::Stage` (Ruffle, the GDraw-like switches on: mipmaps,
smoothing, the deterministic `getTimer`) on one thread of its own (Ruffle's
players are not `Send`; the game calls Iggy from the main and the render
thread). Calls, ticks, size and mouse moves go there; the AS3 external
calls a request made run on the game thread after it (their result in the
movie is `undefined`: `ffx_swf`'s provider answers from a recording).
`IggyPlayerDraw` renders the stage; `FFX_HOST_IGGY_OUT=DIR` writes every
30th image. Without the feature the players are null: no image, the calls
do nothing, which the boot to the title needs no more of (the title menu
is the PS2 menu code, not Flash).

## The C runtime DLLs

The inlined STL templates in `FFX.exe` touch MSVCP110's objects directly
(`basic_ios`, `locale` facets, `basic_string`), so a Rust side must keep
MSVCP110's layouts. Until it does, the player's own `MSVCR110.dll` and
`MSVCP110.dll` (from the game folder, read as data like `FFX.exe`, never in
git) run in Unicorn beside `FFX.exe`, development only (`src/dll.rs`):

- mapped into the arena at the first free 64 KB gap above `0x04000000`
  (both prefer `0x10000000`, where the heap is), relocated
  (`IMAGE_REL_BASED_HIGHLOW`), then `DllMain(DLL_PROCESS_ATTACH)`, MSVCR110
  first, before the entry point; each new thread runs
  `DllMain(DLL_THREAD_ATTACH)` first;
- their `KERNEL32` imports go to the same Rust sides as `FFX.exe`'s
  (`src/win32.rs`: TLS slots in each thread's TEB, Windows-1252 code pages,
  the "C" locale, the standard handles, module handles; `GetProcAddress`
  finds nothing, so MSVCR110 takes its `Tls*` fallbacks for `Fls*`);
  `MSVCP110`'s `MSVCR110` imports go straight to the loaded MSVCR110's
  exports;
- `FFX.exe`'s data imports (`_acmdln`, `_fmode`, `_commode`, `_HUGE`)
  point at the DLL's own variables.

Which of `FFX.exe`'s imports go where (`ffx-rust --routes FILE` lists
every one):

| | Rust | DLL | missing |
|---|---|---|---|
| `MSVCR110.dll` (188) | 26: start-up and exit (`__set_app_type`, `__setusermatherr`, `__getmainargs`, `_initterm`, `_initterm_e`, `_onexit`, `__dllonexit`, `__crtGetShowWindowMode`, `_crt_debugger_hook`, `__crtSetUnhandledExceptionFilter`, `_amsg_exit`, `exit`, `_exit`, `_cexit`, `abort`), the heap (`malloc`, `calloc`, `free`, `_recalloc`, `_calloc_crt`), `memset`, `memcpy`, `memmove`, `_strdup`, `rand`, `srand` | the other 162 (`sprintf*`, `fopen`, `fwrite`, `_controlfp_s`, `_lock`, the `_CI*` math intrinsics, ...) | 0 |
| `MSVCP110.dll` (75) | 0 | 75 | 0 |
| the DLLs' own imports (383) | 123 (`KERNEL32`: the stand-ins above) | 170 (MSVCP110 → MSVCR110, all) | 90 (the rest of `KERNEL32`: `FindFirstFileExW`, `CreateProcessW`, timer queues, ...; none called on the way to the device) |

The Rust sides kept are exact: the heap is one heap (the DLL's `malloc`
calls `HeapAlloc`, whose Rust side allocates from the same arena heap as
the Rust `malloc`, so a block can be freed on either side), the copies
allow overlap as MSVCR110's do, and `rand` keeps MSVC's sequence per
thread (seed 1). Everything else goes to the DLL: the Rust `sprintf`,
`fopen`, `_controlfp_s` were approximations.

The DLLs' x87 transcendental instructions run exactly (above, "x87")
and their C++ exceptions dispatch through the SEH chain (above,
"Exceptions").

## Overlays

The spell overlays (`magicFiles/FFX/magic_<nnnn>.dll`,
`docs/formats/magic.md`) are loaded as the game asks for them
(`src/library.rs`, host-battle 2026-10-29): `LoadLibraryA` of a DLL under
`magicFiles` (from `PhyreFIOS_LoadsPrx` or the async task
`MagicDLLAsyncLoad`) reads the player's file from the game folder, maps
it into the arena and relocates it as `src/dll.rs` does the C runtime,
binds each import to where `FFX.exe`'s (or a C runtime DLL's) same import
goes (the IAT slot's value: the same Rust side, so `rand` is the game's
own sequence, or the same DLL export; else `MSVCR110`'s export), and runs
its `DllMain(base, DLL_PROCESS_ATTACH, 0)` on the loading thread; its code
runs in Unicorn like `FFX.exe`'s. `GetProcAddress` finds its exports by
name (`GetEffectOverlayTable`, `InitMagicPRX`; `onMagicDLLLoaded`),
`FreeLibrary` runs `DllMain(base, DLL_PROCESS_DETACH, 0)` and forgets it.
A freed overlay's range is never reused: each thread's Unicorn keeps its
translations by address and doesn't see the host write new code there.
Other libraries (`cg.dll`, `psapi.dll`) still get 0, which the game takes
as absent. Before this, every battle effect that loads an overlay
(magic, overdrives, summons) waited for `g_MagicFile_Handle` forever.
The overlays' x87 sites are not marked (their maths goes through
`_CIatan2` and the `_libm_sse2_*` imports).

**Rust ports** (host-gate, 2026-10-31). The functions `crates/ffx-magic`
ports run as Rust (`src/library.rs`), as the hook's `FFX_MAGIC_RUST`
does (`docs/formats/magic.md`, "Porting the overlays"), and Unicorn runs
only the rest:

- At `LoadLibraryA`, before `DllMain`, every address the game can enter
  the overlay's code by (its exports, its entry point, and every
  relocated word of the image that points into its code: the overlay
  table, stored callbacks, `push offset` operands) is offered to
  `ffx_magic::bind`. Where a port's code identity matches, the address
  gets an `int3` and a trap (`Shared::add_trap`) that runs the port with
  `ffx_magic::Frame` (`esp` at the return address, the registers) on a
  `ffx_magic::Game` over the arena and `Exec::call`. The range is fresh,
  so no thread has translated it yet.
- The port runs 64 KiB below the caller's `esp` (ports keep locals below
  their entry `esp`, docs/formats/magic.md "Locals"); its calls into the
  game push below that. `Ret::pops` picks the return stub, a tail jump
  (`Ret::jump`) resumes at the target with the caller's stack
  (`Exec::trap_exit`), `xmm0` and ST0 results reach the caller. `rand`,
  the `_libm_sse2_*_precise` functions (`Exec::call_sse`, `xmm0` in and
  out) and `_CIatan2` (`call_x87`) go where the DLL's own imports go, so
  the results are the game's. A call from Rust into a bound address
  (`DllMain` at the load, `GetProcAddress` results) puts its words on the
  game stack first, where the port reads them.
- `FFX_MAGIC_RUST` picks the DLLs as in the hook, but on by default:
  unset or `1` every DLL, `0` none (all Unicorn), or a comma list of
  numbers. `ffx_host::library::select_rust` does the same for tests.
- **Counted per entry**: the traps count Rust calls; a block hook on the
  overlay's code (each thread's emulator gets it before it next runs)
  counts the entries without a port that ran in Unicorn. Each overlay's
  counts are noted at `FreeLibrary` (`overlay calls: magic_0481.dll rust
  N (k entries bound), unicorn M (j entries)` and a line per entry that
  ran), the rest and the totals at the harness's `quit` and in the report
  (`overlay calls in all`); `run-all.sh` keeps each replay's
  `ffx-rust.log` and prints the totals.
- `tests/overlay.rs` loads `magic_0604` (fully ported) twice through
  `FFX.exe`'s own `LoadLibraryA`, once all in Unicorn and once with the
  ports: `InitMagicPRX` and `GetEffectOverlayTable` called from Rust and
  from emulated code give the same results and leave the same data but
  the CRT's own words (the cookie, the attach count, the `onexit` table,
  which the ported `DllMain` keeps none of), 5 calls in Rust and none in
  Unicorn on one side, the other way round on the other.

## Threads

Every game thread is a host thread with its own `Exec` (`src/exec.rs`):
its own Unicorn instance (Unicorn is single-threaded) mapping the same
arena regions, its own stack region (1 MB; the main thread 2 MB), thread
block (GDT, TEB with the TLS slots, PEB) and return stubs (the float
result cell is per thread). `Shared` holds what they share: the arena, the
image, the DLLs, the function table, the import bindings (read-only), the
heap (behind a lock), the files, the synchronisation objects.

- `CreateThread(attr, stack, entry, param, flags, &id)` starts a host
  thread that runs `DllMain(DLL_THREAD_ATTACH)` and then `entry(param)`
  (stdcall); `CREATE_SUSPENDED` waits for `ResumeThread`. The thread
  handle is signalled when the routine returns or calls `ExitThread`;
  `GetExitCodeThread` gives its code. `SubmitThreadpoolWork` runs the work
  item's callback on a thread of its own the same way.
- Synchronisation maps onto host primitives (`src/sync.rs`, one lock and
  one condition variable for all objects): events (manual and auto
  reset), semaphores, mutexes, thread handles, `WaitForSingleObject(Ex)`,
  `WaitForMultipleObjects`, and critical sections keyed by the game
  address of their `CRITICAL_SECTION` (owner and recursion count, so
  `TryEnterCriticalSection` and recursion behave). `Interlocked*` are host
  atomics on the arena word. `Sleep` really sleeps.
- Regions mapped at run time (`VirtualAlloc`, another thread's stack) are
  mapped into each thread's emulator before it next runs (the arena keeps
  a generation counter).
- Stopping: a failure on a game thread ends that thread (its handle is
  signalled, the report gives its outcome and return addresses); a failure
  on the main thread, a milestone, `exit` or the budget end the run. A
  watchdog thread then calls Unicorn's `uc_emu_stop` (thread-safe) on
  every live emulator, waits wake up within 50 ms, and every thread
  unwinds.
- Emulated `lock`-prefixed instructions are atomic within one Unicorn
  instance only; the game's own synchronisation goes through the imports
  above, which is what keeps the threads apart.

`tests/boot.rs`'s
`game_threads_run_in_parallel_under_the_games_own_critical_section`
proves it on emulated code: two threads started through `FFX.exe`'s own
`CreateThread` import each add to one counter 3,000 times with a plain
`inc` under one critical section (through the game's IAT), and the main
thread waits on both thread handles: the count is exactly 6,000.

## Windows

`src/win_forward.rs` binds ahead of the stand-ins on Windows
(`imports::platform_table`):

- **The window.** `RegisterClassA` registers a real class of the game's
  name whose procedure is a Rust function (`host_wndproc`); the game's
  procedure (`Phyre_PFramework_PWindowWin32Base_WndProc`, `0x00625130`) is
  kept by class. `CreateWindowExA` makes the real window with the game's
  strings, styles and size, then gives the game's procedure its
  `WM_CREATE` with a `CREATESTRUCTA` in the arena, as Windows would have
  during the call. The game holds the real `HWND` (32 bits on i686; the
  handle table maps it at stage 4).
- **Messages.** `PeekMessageA/W` peek the real queue into the game's
  `MSG`; `DispatchMessageA/W` of a message for the game's window calls
  the game's procedure through `Exec::call` (emulated or ported), other
  windows' messages go to the real `DispatchMessage`. What Windows sends
  to the window (`WM_SIZE`, `WM_ACTIVATE`) arrives in `host_wndproc` on
  the game's main thread with no executor at hand: it is queued and given
  to the game's procedure at its next `PeekMessage`. `WM_CLOSE` is not
  given to the game (its handler starts the Steam launcher,
  `ShellExecuteA`): it ends the run. `DefWindowProcA`, `SendMessageA/W`
  (the game's window: its procedure), `PostMessageA`, `PostQuitMessage`,
  `Set/GetWindowLongA` (the window procedure slot kept by the host),
  `GetClientRect`, `GetWindowRect`, `AdjustWindowRect`, `ClientToScreen`,
  `SetWindowTextA`, `UpdateWindow`, `DestroyWindow`, `ShowCursor`,
  `GetSystemMetrics` and `GetClipCursor` forward.
- **Background mode** (`FFX_HARNESS_BACKGROUND=1`): the window is made
  without `WS_VISIBLE`, `ShowWindow` shows it without activating it and
  puts it at the bottom of the stack, `SetWindowPos` never raises or
  activates it, `GetCursorPos` reads a point far outside the window, and
  `SetCursorPos`/`ClipCursor` never touch the user's pointer (always, for
  now).
- **Timers.** `timeBeginPeriod`/`timeEndPeriod` forward, so `Sleep` has
  the 1 ms granularity the game asks for (its threads poll with
  `Sleep(1)`: 7,755 calls on the way to the third frame), not Windows'
  default 15.6 ms.
- **Memory.** On i686 a region (`VirtualAlloc`, a thread's stack) goes
  into the first free gap of the process's own address space, which the
  GPU driver fills with reservations of hundreds of MB. Probing those 64 KB
  at a time made each of the boot's 765 `VirtualAlloc`s take tens of ms:
  190 s to the third `Present`. `Arena::map_anywhere` now jumps past what
  `VirtualQuery` says holds a refused address: 27 s (Linux: 7 s).
- **Input.** `DirectInput` stays the layer's (no devices: the real
  keyboard, mouse and pads never reach the game); the harness's `keys`
  fill the keyboard's `GetDeviceState`. XInput is never called (the game
  makes XInput devices only for controllers `DirectInput` enumerates).
- **Files** were already real: the game folder (the executable's folder
  by default) through `std::fs`, read-only, and the Documents folder
  (`--documents`, or the harness's `FFX_HARNESS_HOME`) read-write.

## Building for Windows

`tools/build-host.sh` (`build`, or `clippy` with cargo's arguments after
it) builds `ffx-rust.exe` for i686 through cargo xwin, like the hook.
Unicorn's C build needs cmake, ninja and `llvm-lib`, and cargo-xwin's
cmake toolchain file sets `CMAKE_MSVC_RUNTIME_LIBRARY`, which unicorn's
`CMakeLists.txt` refuses next to the `-MT` that `cc` passes. The script
supplies cmake and ninja through `uvx` when they are missing, links the
versioned `llvm-lib-<n>`, and points `CMAKE_TOOLCHAIN_FILE_i686-pc-windows-msvc`
at a copy of the toolchain file without that line (all under
`target/host-shims`). `build.rs` links the program at `/BASE:0x70000000`
with `/LARGEADDRESSAWARE`, so the image range is free and the arena can
use the upper 2 GB. `FFX_HOST_TARGET=x86_64-pc-windows-msvc` builds the
64-bit program instead (the arena with a base, stage 4); Unicorn's
`setjmp` wrapper is MASM there, assembled by LLVM's `llvm-ml64` under the
name `ml64`.

  it. `src/tcg_commit.rs` registers a handler of our own in front of

  Unicorn makes, are touched.

#### The cloth race (2026-10-31, host-gate)

What differs between runs on the cloth (event-besaid-4/-5 on Tidus's hood
and the mesh on his leg, boot-3 on Rikku's strap, kami0100's cloth ring,
battle-magic-3 once; originals now and then, ffx-rust.exe more often) is
the order of two copies of the cloth vertices on two threads, measured
on PC2 with `FFX_HOST_WATCH` (event-besaid, 424 updates; threads: main
`0x1004`, render `0x100c`, JobWorkers `0x1010`-`0x101c`):

1. **The step** (JobWorkers): `Ch_DrawMain` (`0x0082ed50`) queues one
   `Ch_Cloth_PerCharacter` job per cloth character late in each update
   (`JobSchedule_Ch_Cloth_PerCharacter` `0x00a44b40`); `Sg_ClothStep`
   (`0x00822de0`) writes the character's cloth vertex buffer (the cloth
   record's `+0x4c`). `Sg_MainLoop` waits for the jobs at its end
   (`JobScheduleWait_Ch_Cloth_PerCharacter`, 422 waits, all on the main
   thread). So the step itself never races the main thread's reads.
2. **The submit** (main thread, after the update): `FFXApplication_render`
   (`0x0042f930`) runs `graphicCharacterInstanceSetClothVertexBuffers`
   (`0x0063b740`, 424 calls) and `batchSetClothVertexBuffers`, which hand
   each cloth-instancing mesh the live buffer's address
   (`ClothInstancingDynamicMesh_setSlotBuffer_006e2ac0`, `+0xc10 + 4i`);
   then, still on the main thread while it builds the frame's render
   commands, the instance's vtable slot 2,
   `ClothInstancingDynamicMesh_submit_006e28f0` (4,530 calls), copies the
   live buffer into the slot's staging buffer `+0x210`, **but only when
   the slot's flag `+0x810 + 4i` is set** (`InterlockedCompareExchange(flag,
   0, 1)`), and clears the flag.
3. **The stage** (render thread, when it draws that update):
   `ClothInstancingDynamicMesh_stageStreams_006e2000` (mesh slots 5 and 6,
   from the renderer's dynamic streams; 1,807 calls, all on the render
   thread) copies the staging buffer into the draw's vertex stream and
   sets the slot's flag again.

The render thread draws update `n` while the main thread runs update
`n + 1` (`docs/harness.md`, "Frames and threads"). If the render thread
has staged slot `i` of update `n` before the main thread's submit of
update `n + 1` reaches it, the flag is set and update `n + 1`'s vertices
are copied; if not, the submit skips the slot and update `n + 1` draws
the vertices of `n` again: that slot is a step behind. The slots of one
character (the hood, the leg mesh) go either way independently, which is
the "dark notch" and the half-old hood. Natively the render thread is
almost always done first; under emulation it is slower (the watch shows
frame 301's stages 2.7 s after the main thread's submits), so
ffx-rust.exe skips more often.

**Measured**: event-besaid on ffx-rust.exe, the same build, back to back
on PC2: without an order shot 4 differed from both originals by 2,087
pixels (x 310..446, y 434..709, the hood and the leg); with
`FFX_HARNESS_CLOTH_ORDER=1` all five shots matched with 0 pixels and the
trace had the original's events. (In the main-list run before them shot
4 happened to match without it.)

**The order for both programs (the plan; nothing re-recorded).** In
lockstep, before the main thread's cloth submits of update `n + 1`, every
flip queued before them must have been presented (the render thread has
staged update `n`), so each submit finds its flag set and copies:

- ffx-host does it now as an experiment, `FFX_HARNESS_CLOTH_ORDER=1`
  (`harness.rs` `cloth_order`, `stats`' `cloth_waits`): the cloth job of
  update `n + 1` waits until the presented flips (`after_present_flip`)
  reach the queued ones (the flip wrapper's count), at most 2 s, then
  goes on with a note. The main thread waits for the jobs before it
  submits, so the stage of `n` comes before the submit of `n + 1`. A
  cleaner place for the same wait is the wrapper of
  `graphicCharacterInstanceSetClothVertexBuffers` (main thread, right
  before the submits): no wait on a JobWorker, and it covers a frame
  with cloth meshes but no cloth job.
- The hook needs the same wait in its harness (its flip wrapper already
  labels the flips and its `Present` wrapper sees each one done), then
  `FFX_HARNESS_CLOTH_ORDER` (or always on in lockstep) for both.
- No deadlock: the present of update `n` waits only until the main
  thread has left boundary `n`, which it has while it runs update
  `n + 1`; the 2 s limit and its note are there in case a lock proves
  otherwise.

**Which replays need re-recording**: the order chosen is the one the
originals show almost always (event-besaid-4 matched the existing
references pixel for pixel with it), so none is expected to. The
coordinator's check once the hook has the wait: run the original code of
the replays with cloth on screen twice each and re-record only those
whose shots then differ from the current references: event-besaid
(shots 4, 5), boot (3: Rikku's strap), battle-magic (3), battle-attack,
battle-overdrive, battle-ifrit, field-walk and event-arrival (Tidus), and
the draw gates with cloth, draw-gate-kami (kami0100's ring, `vb5`) and
draw-gate-besaid with their `dg-*` references; the cloth-ring and hood
entries of the accepted residue (`docs/harness.md`, "Accepted residue")
and of the scene-gate allow lists should then go. The menu replays draw
no cloth character.

#### The i686 build: a case for dropping it (2026-10-31, host-gate)

The i686 `ffx-rust.exe` still ends a few seconds past its third frame in
Unicorn's 32-bit x86 TCG backend (`tcg_reg_alloc`, no free host
register: an `abort` inside QEMU's code generator, "Status on Windows").
Not chased further, for these reasons:

- **Stage 4 is 64-bit, and the 64-bit build is the one that runs.** Every
  replay of the stage 3 gate ran on the x86_64 build (above), and the M5
  decisions put the program at 64 bits for good (`docs/rewrite-plan.md`,
  "M5: inversion"). The i686 build was the stage 3 stepping stone: "any
  difference is the host's" holds just as well for the 64-bit arena,
  whose ports are the same code over `Mem`.
- **The abort is in Unicorn, which goes before the release.** It is QEMU's
  32-bit host backend running out of registers on one of the game's
  blocks; fixing it means patching Unicorn's C code (GPL, development
  only) for a host we don't ship, or finding and avoiding the block. When
  the last unported function is gone, so is Unicorn and with it the
  abort.
- **What the i686 build tests that x86_64 doesn't** is that the arena's
  addresses equal host pointers (base 0). The ported shims are written for
  both (the hook is 32-bit and runs them natively), and the 64-bit build
  already caught every case where a shim handed the game a host address
  (blocker 7, the held shims): the stricter target finds more.
- **Cost of keeping it**: `tools/build-host.sh` builds it in every gate
  (a second Unicorn and ffx-host-ports compile), `src/relaunch.rs` (the
  child process with the image range reserved) exists only for it, and
  `docs/harness.md` describes both.

Proposal (the coordinator decides): keep i686 compiling (it is the hook's
target, and the 32-bit clippy covers `ffx-host` too) but drop it from the
host gate's runs and from `tools/run-game.sh --rust`'s default
(`FFX_HOST_TARGET` defaulting to x86_64), and remove `relaunch.rs` when
the i686 build is dropped entirely.
